= 模块 3：智能体应用的指标和日志
:imagesdir: ../assets/images
:navtitle: 模块 3：指标与日志
:toc: macro
:toclevels: 1

指标告诉你系统中发生了*什么*。日志告诉你*确切发生了什么以及何时发生*。在本模块中，你将探索一个预部署的 Grafana 仪表板，该仪表板监控 mortgage-ai 多智能体系统，然后使用 OpenShift 控制台中的 LokiStack 调查应用程序日志。

TIP：在本模块中，你扮演 **SRE / 平台工程角色**，专注于系统健康、请求速率、错误率和操作日志。

== 学习目标

完成本模块后，你将能够：

* 识别对多智能体 AI 系统至关重要的关键指标
* 导航预部署的 Mortgage-AI Grafana 仪表板
* 使用 LokiStack 和日志查询语言（LogQL）探索和过滤应用程序日志
* 解释指标和日志如何协同工作以实现智能体可观测性

== 是什么让智能体指标与众不同？

传统应用程序需要请求速率、错误率和延迟。智能体应用程序需要所有这些*加上*捕获 LLM 行为、代理路由和工具执行的指标。这里有 6 个最重要的指标：

[cols="2,2,3",options="header"]
|===
|指标 |Prometheus 名称 |它告诉你什么

|请求速率和错误
|`http_requests_total`
|我们获得了多少流量？有多少请求失败了？

|延迟百分位数
|`http_request_duration_seconds`
|我们响应有多快？有异常值吗？

|LLM Token使用量
|`llm_tokens_total`
|我们消耗了多少Token？每次对话的成本是多少？

|LLM 推理延迟
|`llm_inference_duration_seconds`
|模型响应需要多长时间？它是瓶颈吗？

|工具调用成功率
|`tool_calls_total`
|代理工具是否工作？哪些失败了？

|代理路由
|`agent_routing_total`
|查询是路由到快速还是能力模型？分类器是否工作？
|===

image::agentic-app-pre4.png[智能体指标 - 最重要的 6 个，显示传统指标加上智能体附加项，包括模型路由和由 OpenShift UWM 进行 Prometheus 抓取,link=self,window=blank,width=700]

mortgage-ai API 以 Prometheus 格式在 `GET /metrics` 处公开所有这些指标。**OpenShift 用户工作负载监控**（Red Hat OpenShift AI 附带的内置 Prometheus 实例）每 30 秒自动抓取它们并将它们存储在时间序列数据库中。

这意味着你不需要自己设置 Prometheus——平台处理收集和存储。你只需要：

1. 从应用程序公开指标（mortgage-ai 已经这样做了）
2. 配置可视化平台（本研讨会中使用 Grafana）来查询 OpenShift Prometheus 数据源（已配置）
3. 构建仪表板来可视化指标（你接下来将探索这一点）

[%collapsible]
.完整指标参考（点击展开）
====
mortgage-ai 后端公开了 `packages/api/src/core/metrics.py` 中定义的 10 个自定义指标：

|===
|Prometheus 名称 |类型 |标签

=== 概览和 HTTP 面板

仪表板的顶部给你系统健康状况的一览：

image::grafana2.png[Grafana 概览和 HTTP 面板，显示请求速率和延迟,link=self,window=blank,width=700]

你看到的内容：

* **总请求数（最近一小时）**：有多少请求访问了 API。在截图中，约 983 个请求。
* **请求速率**：当前每秒吞吐量。
* **错误率（%）**：5xx 响应的百分比。绿色表示健康。
* **P95 延迟**：95% 的请求在此值之前完成。低于 100ms 是极好的。

在概览下方，HTTP 面板按端点和状态代码细分流量。寻找：

* 哪个端点获得最多流量（可能是 `/api/prospect/chat`）
* HTTP 状态分布中的任何黄色（4xx）或红色（5xx）条
* 哪些端点具有最高的 P95 延迟

[%collapsible]
.概览面板的 Prometheus 查询语言（PromQL）详细信息（点击展开）
====
* **请求速率**：`sum(rate(http_requests_total{namespace=~"$namespace"}[5m]))`
* **错误率**：`(sum(rate(http_requests_total{namespace=~"$namespace", status=~"5.."}[5m])) / sum(rate(http_requests_total{namespace=~"$namespace"}[5m])) * 100) or vector(0)`
* **P95 延迟**：`histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket{namespace=~"$namespace"}[5m])) by (le))`

`rate()` 在时间窗口上计算每秒平均值。`histogram_quantile()` 从直方图桶计算百分位数。
====

=== AI 代理指标

向下滚动到 **AI 代理指标** 行。这里开始有趣了。这些指标是智能体应用程序独有的：

image::grafana1.png[Grafana AI 代理指标，显示Token使用和工具调用成功率,link=self,window=blank,width=700]

本部分顶部的 4 个统计面板显示：

* **活动聊天会话**：实时 WebSocket 连接。现在有多少用户在聊天？
* **LLM Token总数**：自 API 启动以来累计消耗的Token。这是你的成本代理，在截图中 18.5K Token。
* **工具调用成功率**：代理工具是否工作？100% 意味着一切健康。
* **平均 LLM 延迟**：LLM 推理调用的中位时间。在截图中 1.75s。

在统计下方，详细信息面板显示：

* **按模型的 LLM Token使用量**：哪个模型消耗最多Token？输入还是输出占主导地位？
* **按角色的 LLM 推理延迟**：哪个代理角色最慢？慢的承保代理可能表示复杂的合规工具调用。
* **代理路由分布**：简单与复杂路由的饼图。复杂查询的高比率意味着能力模型在做大部分工作。
* **按状态的工具调用**：绿色表示成功，红色表示失败。红色峰值意味着工具集成正在中断。

[%collapsible]
.AI 代理指标的 PromQL 详细信息（点击展开）
====
* **LLM Token**：`sum(increase(llm_tokens_total{namespace=~"$namespace"}[1h]))`
* **工具成功率**：`(sum(tool_calls_total{namespace=~"$namespace", status="success"}) / sum(tool_calls_total{namespace=~"$namespace"}) * 100) or vector(100)`
* **LLM 延迟**：`histogram_quantile(0.50, sum(rate(llm_inference_duration_seconds_bucket{namespace=~"$namespace"}[5m])) by (le))`
* **路由分布**：`sum(agent_routing_total{namespace=~"$namespace"}) by (complexity)`
====

== 练习 2：使用 LokiStack 探索应用程序日志

指标显示聚合健康，但当出现问题时你需要实际的日志事件。Red Hat AI 包含 **LokiStack**，一个高性能日志聚合系统，它自动收集应用程序写入 STDOUT 或 STDERR 的所有内容——无需更改代码。让我们探索 mortgage-ai 日志。

=== 导航到日志查看器

. 导航到 *OCP 控制台* 标签页。然后导航到 **观察** → **日志**。
+
image::observe-logs.png[]
+
你将看到 **禁止 - 缺少获取日志的权限** 错误：
+
image::logging4.png[OpenShift 控制台观察日志，显示普通用户的禁止错误,link=self,window=blank,width=700]
+
这是预期的。因为你以普通用户（`{user}`）身份登录，OpenShift 出于安全考虑将日志访问限制为仅你的命名空间。集群范围的日志访问保留给集群管理员。

=== 将日志范围限定到你的命名空间

[start=2]
. 点击 **显示查询** 以打开查询编辑器：
+
image::logging5.png[OpenShift 控制台日志显示查询按钮,link=self,window=blank,width=700]
+
输入此 LogQL 查询以将日志范围限定到你的命名空间：
+
[source,logql,role=execute,subs=attributes+]
----
{ log_type="application", kubernetes_namespace_name="{user_project}" }
----
+
点击 **运行查询**。你现在应该看到来自 mortgage-ai Pod 的日志。
+
TIP：`log_type="application"` 过滤掉基础设施日志（kubelet、CRI-O）。`kubernetes_namespace_name` 标签由日志收集器自动注入。

=== 理解日志格式

你看到的是结构化 JSON。每个日志条目包含：

* **Kubernetes 元数据**：Pod ID、容器名称、命名空间标签、网络配置
* **应用程序消息**：来自应用程序的实际日志事件（在 `message` 字段中）
* **时间戳**：事件发生的时间

滚动日志条目以查找 `message` 字段——这是有用的应用程序数据所在的位置。元数据帮助跨容器关联日志并按 Pod、命名空间或容器进行过滤。

TIP：要快速定位日志条目中的 `message` 字段，请使用浏览器的查找功能：**Cmd+F** (Mac) 或 **Ctrl+F** (Windows/Linux)，然后搜索 `"message"`。这有助于你跳过 Kubernetes 元数据并直接跳转到应用程序日志内容。

=== 提取应用程序消息

[start=3]
. 使用 LogQL 仅提取应用程序消息并过滤到 API 容器日志：
+
[source,logql,role=execute,subs=attributes+]
----
{ log_type="application", kubernetes_namespace_name="{user_project}", kubernetes_container_name="api" }
| json
| line_format "{{.message}}"
----
+
这将删除 Kubernetes 元数据并仅显示应用程序写入其日志的内容。

=== AI 如何帮助进行日志分析

原始日志包含丰富的数据，但手动解析 JSON 很繁琐。在生产环境中，团队可以使用 AI 驱动的可观测性工具来提取见解：

**AI 助手可以使用这些日志做什么：**

* "显示过去一小时内来自 CEO 代理的所有错误"
* "下午 2 点是什么导致了延迟峰值？"
* "总结今天的失败工具调用"

**AI 生成的见解示例：**

[source,text]
----
mortgage-ai 日志分析（最近一小时）：
• 42 个工具调用：40 个成功，2 个失败
• 失败：get_credit_score 超时（30s）
• 最慢的工具：get_pipeline_summary（平均 2.3s）
• 最活跃的代理：潜在客户（27 个请求）
----

原始数据存在于 LokiStack 中——AI 使其可访问而无需手动 JSON 解析或复杂查询。

=== 日志和跟踪是互补的

日志捕获详细事件：错误、警告、调试输出、工具结果。它们对于以下内容至关重要：

* 调试特定失败（"错误消息是什么？"）
* 审计合规事件（"谁访问了此 PII？"）
* 调查意外行为（"为什么此计算返回零？"）

**模块 4 介绍跟踪**，它通过提供以下内容来补充日志：

* 跨代理和工具的分层请求流程
* 每个步骤的时间细分
* 显示什么调用什么的父子关系

一起，日志和跟踪给你完整的可见性：日志用于详细事件，跟踪用于请求流程。

IMPORTANT：**LokiStack 是 Red Hat AI 的支持功能。** 日志在 Pod 生命周期之外持久存在——当容器重启或重新部署时，LokiStack 保留历史日志，使事后调查成为可能。对于多智能体系统，这种持久日志存储对于跨 API、UI 和数据库容器关联事件至关重要。
