== CEOの会話を振り返る

モジュール 1 で、あなたが CEO アシスタントに「ポートフォリオの健全性は？」と尋ねたときのことを覚えていますか？ そのたった 1 つの質問から、パイプラインの統計とメトリクスを含む洗練された応答が生成されました。しかし、裏では実際に何が起こっていたのでしょうか？

**あなたの質問は以下をトリガーしました：**

* **30 以上のメトリクス**: トークン数、LLMのレイテンシ、データベースのクエリ時間、ツール呼び出しの所要時間
* **15 以上のログイベント**: エージェントの意思決定、ツールのパラメーター、プロンプト/コンプリーションのペア、データベースの結果
* **1 つの分散トレース**: CEO エージェントのワークフロー全体で、5 回以上の LLM 呼び出しと 3 回以上のツール呼び出しにまたがるもの

あなたが見たのは最終的な答えだけでした。どのツールが呼び出されたのか、各ステップにどれくらいの時間がかかったのか、呼び出しが失敗したかどうかなどの意思決定プロセスは、完全に目に見えないままでした。

**これが、実際に起きているオブザーバビリティのギャップです。**

このモジュールでは、目に見えない意思決定プロセスを可視化する、オブザーバビリティの 3 本柱（メトリクス、ログ、トレース）について学びます。Fed Aura Capital が、問題をデバッグし、パフォーマンスを最適化し、品質を確保するために、CEO の会話から何をキャプチャする必要があるのかを理解します。

NOTE: これは概念的なモジュールであり、ターミナルやクラスターでの作業は必要ありません。モジュール 3〜6 で実践的なツールについて深く掘り下げる前に、共通の語彙を構築することが目的です。

== 学習目標

このモジュールを修了すると、以下のことができるようになります：

* オブザーバビリティの 3 本柱であるメトリクス、ログ、トレースを定義できる
* それぞれの柱がマルチエージェント AI システムにどのように特有の形で適用されるかを説明できる
* SRE/プラットフォームエンジニアとAI開発者/エンジニアのオブザーバビリティのニーズの違いを区別できる
* Fed Aura Capital において、オブザーバビリティツールをペルソナ固有のユースケースにマッピングできる

== オブザーバビリティの 3 本柱

ツールや実装について詳しく説明する前に、エージェント型 AI システムのコンテキストにおけるオブザーバビリティの共通語彙を確立しましょう。

=== 柱 1: メトリクス (Metrics)

**定義**: システムの状態を表すために一定間隔で収集される数値による測定値。

**従来のシステムの場合**:

* CPU 使用率、メモリ使用量、リクエスト率
* エラー率、レイテンシのパーセンタイル
* キューの深さ、接続数

**エージェント型 AI システムの場合**:

* リクエストごとのエージェントあたりのトークン使用量
* LLM 推論のレイテンシ
* エージェントの意思決定の信頼度スコア
* MCP ツール呼び出しの成功/失敗率
* エージェントのハンドオフ（引き継ぎ）の頻度
* モデル応答の品質スコア

=== 柱 2: ログ (Logs)

**定義**: タイムスタンプが付与された、不連続なイベントの不変の記録。

**従来のシステムの場合**:

* アプリケーションのエラーと例外
* アクセスログ、監査証跡
* デバッグ情報

**エージェント型 AI システムの場合**:

* エージェントの推論チェーンと意思決定の根拠
* デバッグ用のプロンプト/コンプリーションのペア
* ツールの呼び出しパラメーターと応答
* コンプライアンス監査イベント (Fed Aura Capital にとって非常に重要！)
* エージェントの状態遷移

=== 柱 3: トレース (Traces)

**定義**: リクエストが分散システムを通過する際の経路の記録。

**従来のシステムの場合**:

* サービス間の呼び出しチェーン
* データベースクエリの実行パス
* 外部 API との統合

**エージェント型 AI システムの場合**:

* マルチエージェントワークフローの実行パス
* プロンプト/コンプリーションを含む LLM 推論のスパン
* MCP ツール呼び出しチェーン
* エージェント間のハンドオフシーケンス
* 入力から出力までの完全な意思決定パス

== 演習 1: 柱を Fed Aura Capital のニーズにマッピングする

これらの概念を Fed Aura Capital のマルチエージェント住宅ローンシステムに適用してみましょう。

. オブザーバビリティのニーズのマッピングを確認します：
+
[cols="1,1,2",options="header"]
|===
|柱 |従来のニーズ |Fed Aura Capital の AI のニーズ

|メトリクス (Metrics)
|リクエスト率、エラー率
|エージェントのトークン消費量、モデルのレイテンシ、コンプライアンスチェックの合格率

|ログ (Logs)
|エラーメッセージ
|エージェントの推論チェーン、コンプライアンス監査証跡、PII（個人情報）アクセスログ

|トレース (Traces)
|サービスコールグラフ
|5つのエージェントにまたがるローン申し込みフロー、MCPツールの実行パス
|===

. 各質問に答えるためにどの柱が役立つかを特定します。答えを見る前に考えてみてください：

* 「今日、ローン申し込みの処理でトークンをいくつ消費しましたか？」
+
[%collapsible]
====
*メトリクス*: トークン使用量カウンターにより、時間の経過に伴う消費量を追跡します。
====

* 「モデルの設定をアップグレードした後、API が失敗しているのはなぜですか？」
+
[%collapsible]
====
*ログ*: エラーの詳細と設定の不一致は、ログイベントに記録されます。
====

* 「ローン処理パイプラインのボトルネックはどこですか？」
+
[%collapsible]
====
*トレース*: エンドツーエンドのリクエストトレースにより、どのエージェントまたはツール呼び出しが最も遅いかが明らかになります。
====

* 「コンプライアンスチェックサービスは劣化していますか？」
+
[%collapsible]
====
*メトリクス*: レイテンシのパーセンタイルとエラー率の傾向により、時間の経過に伴う劣化が示されます。
====

* 「申し込み番号 #12345 の完全な経路はどうでしたか？」
+
[%collapsible]
====
*トレース*: 分散トレースにより、すべてのエージェントにまたがる完全なリクエストフローが再構築されます。
====

== 演習 2: 2つのペルソナ、1つのオブザーバビリティスタック

Fed Aura Capital では、2つの主要なチームがオブザーバビリティを必要としていますが、注目するポイントが異なります。AgentOps オブザーバビリティスタックにおいて、誰が何を所有しているかを特定しましょう。

image::arch2.png[AgentOps Observability Stack showing SRE and AI Developer personas,link=self,window=blank,width=700]

このスタックは両方のペルソナにサービスを提供します：

* **SRE / プラットフォームエンジニアリング**: システムの健全性、SLO、キャパシティ。Red Hat OpenShift AI (RHOAI) Observability Stack、OpenShift Logging、および Grafana ダッシュボードを使用します。
* **AI 開発者 / エンジニア**: モデルの動作、意思決定の品質、エージェントのパフォーマンス。MLflow Tracing、MLflow Evaluations、および Grafana ダッシュボードを使用します。
* **Grafana / Perses ダッシュボード**: メトリクスと KPI の可視化のために、両方のペルソナによって共有されます。

以下の各シナリオについて、どちらのペルソナが責任を持つかを決定してください。クリックすると答えが表示されます：

* 「MLflow トラッキングサーバーのディスク容量が不足しています」
+
[%collapsible]
====
*SRE/プラットフォームエンジニアリング*: インフラストラクチャとストレージの管理。
====

* 「モデルの更新後、ローンの承認率が 15% 低下しました」
+
[%collapsible]
====
*AI 開発者/エンジニア*: モデルの動作の変化には、出力とトレースの調査が必要です。
====

* 「アンダーライターエージェントの P99 レイテンシが SLO を超過しました」
+
[%collapsible]
====
*SRE/プラットフォームエンジニアリング*: SLO の追跡とパフォーマンスの監視。
====

* 「エージェントが、似たような問い合わせに対して一貫性のないアドバイスを提供しています」
+
[%collapsible]
====
*AI 開発者/エンジニア*: 出力品質とプロンプトのデバッグ。
====

* 「MCP サーバーの Kubernetes ポッドが再起動を繰り返しています」
+
[%collapsible]
====
*SRE/プラットフォームエンジニアリング*: ポッドの健全性とインフラストラクチャのトラブルシューティング。
====

* 「コンプライアンスチェックのエージェントが、誤検知（フォールスポジティブ）を多く出しすぎています」
+
[%collapsible]
====
*AI 開発者/エンジニア*: エージェントの意思決定ロジックと評価のチューニング。
====

一部の問題では、両方のペルソナのコラボレーションが必要です：

--
* **レイテンシの急増**: SRE が症状（高いレイテンシ）を特定し、AI 開発者が原因（複雑なプロンプト、モデルの問題）を調査します。
* **エラー率の増加**: SRE がメトリクスを確認し、AI 開発者が失敗したトレースを分析します。
* **リソースの枯渇**: SRE がキャパシティを管理し、AI 開発者がトークン使用量を最適化します。
--

== モジュールのまとめ

**達成したこと:**

* オブザーバビリティの 3 本柱（メトリクス、ログ、トレース）を、エージェント型 AI のニーズにマッピングしました
* オブザーバビリティスタックにおける SRE と AI 開発者の責任の違いを特定しました
* 両方のペルソナがコラボレーションすべき領域を認識しました

**重要なポイント:**

* メトリクス、ログ、トレースはそれぞれ固有の目的を持っています。エージェント型アプリでは、トークン使用量、エージェントの推論、およびマルチエージェントワークフローのパスが追加されます。
* SRE/プラットフォームエンジニアはシステムの健全性に焦点を当て、AI 開発者はモデルの動作に焦点を当てます。
* 効果的な AgentOps には、両方のペルソナ間のコラボレーションが必要です。
