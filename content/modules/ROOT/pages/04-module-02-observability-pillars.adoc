== The three pillars of observability

Before diving into tools and implementation, let's establish a shared vocabulary for observability in the context of agentic AI systems.

=== Pillar 1: Metrics

**Definition**: Numeric measurements collected at regular intervals that represent the state of a system.

**For traditional systems**:

* CPU utilization, memory usage, request rate
* Error rates, latency percentiles
* Queue depths, connection counts

**For agentic AI systems**:

* Token usage per agent per request
* LLM inference latency
* Agent decision confidence scores
* MCP tool call success/failure rates
* Agent handoff frequencies
* Model response quality scores

=== Pillar 2: Logs

**Definition**: Timestamped, immutable records of discrete events.

**For traditional systems**:

* Application errors and exceptions
* Access logs, audit trails
* Debug information

**For agentic AI systems**:

* Agent reasoning chains and decision rationale
* Prompt/completion pairs for debugging
* Tool invocation parameters and responses
* Compliance audit events (critical for Acme FinTech!)
* Agent state transitions

=== Pillar 3: Traces

**Definition**: Records of the path of a request as it propagates through a distributed system.

**For traditional systems**:

* Service-to-service call chains
* Database query execution paths
* External API integrations

**For agentic AI systems**:

* Multi-agent workflow execution paths
* LLM inference spans with prompt/completion
* MCP tool call chains
* Agent-to-agent handoff sequences
* Complete decision paths from input to output

== Two personas, different needs

At Acme FinTech, two primary teams need observability, but their focus areas differ significantly.

=== Persona 1: SRE/Platform Engineering

**Focus**: System health, reliability, and performance

**Primary concerns**:

* Is the system up and responsive?
* Are we meeting our SLOs (Service Level Objectives)?
* Do we have capacity for current and projected load?
* Are there any infrastructure issues affecting agents?

**Key questions they ask**:

* "What's our P99 latency for loan processing?"
* "How much GPU/memory are the inference services using?"
* "Are any pods restarting frequently?"
* "What's our error budget status?"

**Tools they use**:

* Grafana/Perses dashboards for metrics visualization
* Prometheus for metrics collection and alerting
* OpenShift monitoring stack
* On-call alerting systems

=== Persona 2: AI Developer/Engineer

**Focus**: Model behavior, decision quality, and agent performance

**Primary concerns**:

* Are agents making correct decisions?
* What's the quality of LLM outputs?
* Why did an agent behave unexpectedly?
* How can I improve agent performance?

**Key questions they ask**:

* "What prompt led to this unexpected response?"
* "Which agent in the chain made the wrong decision?"
* "What was the confidence score for rejected applications?"
* "Are there patterns in failed compliance checks?"

**Tools they use**:

* MLflow for tracing and experiment tracking
* LLM evaluation frameworks
* Prompt debugging tools
* Agent workflow visualization

== Troubleshooting

**Issue**: Cannot access OpenShift monitoring dashboards
**Solution**:

. Verify your user has monitoring access: `oc auth can-i get pods -n openshift-monitoring`
. Check if monitoring stack is deployed: `oc get pods -n openshift-monitoring`
. Request elevated permissions from cluster admin if needed

**Issue**: No RHOAI dashboards visible
**Solution**:

. Verify RHOAI is installed: `oc get csv -n redhat-ods-operator`
. Check if monitoring is enabled in RHOAI configuration
. Dashboards may require specific RHOAI components to be deployed

**Issue**: Prometheus port-forward fails
**Solution**:

. Check if you have network access: `oc get svc -n openshift-monitoring`
. Try using the route instead: `oc get route -n openshift-monitoring`
. Use the OpenShift console UI as an alternative
