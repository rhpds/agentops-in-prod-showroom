== 重温你的 CEO 对话

还记得你在模块 1 中问 CEO 助手"投资组合健康状况如何"吗？这个问题产生了一个包含流水线统计和指标的精致回答。但实际上幕后发生了什么？

**你的问题触发了：**

* **30+ 个指标**：令牌计数、LLM 延迟、数据库查询时间、工具调用持续时间
* **15+ 个日志事件**：代理决策、工具参数、prompt/完成对、数据库结果
* **1 个分布式跟踪**：跨越 CEO 代理工作流程中的 5+ 个 LLM 调用和 3+ 个工具调用

你只看到最终答案。决策过程——调用了哪些工具、每步花费多长时间、是否有任何调用失败——完全不可见。

**这就是可观测性差距的实际表现。**

在本模块中，你将学习使不可见的决策过程可见的 3 个可观测性支柱（指标、日志、跟踪）。你将了解 Fed Aura Capital 需要从你的 CEO 对话中捕获什么来调试问题、优化性能并确保质量。

NOTE：这是一个概念性模块：不需要终端或集群工作。目标是在模块 3-6 中深入实践工具之前建立共享词汇。

== 可观测性的 3 个支柱

在深入工具和实现之前，让我们在智能体 AI 系统的背景下为可观测性建立共享词汇。

=== 支柱 1：指标

**定义**：以定期间隔收集的表示系统状态的数值测量。

**对于传统系统**：

* CPU 利用率、内存使用率、请求速率
* 错误率、延迟百分位数
* 队列深度、连接计数

**对于智能体 AI 系统**：

* 每个代理每个请求的令牌使用量
* LLM 推理延迟
* 代理决策置信度分数
* MCP 工具调用成功/失败率
* 代理移交频率
* 模型响应质量分数

=== 支柱 2：日志

**定义**：离散事件的时间戳不可变记录。

**对于传统系统**：

* 应用程序错误和异常
* 访问日志、审计跟踪
* 调试信息

**对于智能体 AI 系统**：

* 代理推理链和决策基本原理
* 用于调试的 prompt/完成对
* 工具调用参数和响应
* 合规审计事件（对 Fed Aura Capital 至关重要！）
* 代理状态转换

=== 支柱 3：跟踪

**定义**：请求在分布式系统中传播时的路径记录。

**对于传统系统**：

* 服务到服务调用链
* 数据库查询执行路径
* 外部 API 集成

**对于智能体 AI 系统**：

* 多智能体工作流程执行路径
* 带有 prompt/完成的 LLM 推理跨度
* MCP 工具调用链
* 代理到代理移交序列
* 从输入到输出的完整决策路径

== 练习 2：2 个角色，一个可观测性技术栈

在 Fed Aura Capital，2 个主要团队需要可观测性但关注不同的东西。让我们识别 AgentOps 可观测性技术栈中谁拥有什么。

image::arch2.png[AgentOps 可观测性技术栈，显示 SRE 和 AI 开发者角色,link=self,window=blank,width=700]

* **SRE / 平台工程**：系统健康、SLO、容量。使用 Red Hat OpenShift AI (RHOAI) 可观测性技术栈、OpenShift 日志和 Grafana 仪表板。
* **AI 开发者 / 工程师**：模型行为、决策质量、代理性能。使用 MLflow 跟踪、MLflow 评估和 Grafana 仪表板。
* **Grafana / Perses 仪表板**：由两个角色共享，用于指标和 KPI 可视化。

某些问题需要两个角色之间的协作：

--
* **延迟峰值**：SRE 识别症状（高延迟），AI 开发者调查原因（复杂的 prompt、模型问题）
* **错误率增加**：SRE 看到指标，AI 开发者分析失败的跟踪
* **资源耗尽**：SRE 管理容量，AI 开发者优化令牌使用
