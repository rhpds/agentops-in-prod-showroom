[NOTE]
====
**このモジュールはオプションであり**、モジュール 5 に基づいて構築されています。継続的な品質監視のために、評価を CI/CD パイプラインに自動化する方法を示します。
====

モジュール 5 では、AI 開発者のワークフローの*インナーループ*である Jupyter ノートブックから手動で評価を実行しました。しかし、手動での評価はスケーラブルではありません。本番環境では、自動的に、スケジュールに基づいて、または CI/CD パイプラインの一部として実行される評価が必要です。

このモジュールでは、Red Hat OpenShift AI に評価パイプラインをインポートして実行することで、インナーループから*アウターループ*へと移行します。モジュール 5 で使用したのと同じスコアラー、データセット、および MLflow 統合が、自動化されたパイプラインとして実行されます。ノートブックは必要ありません。

TIP: このモジュールでは、あなたは**両方の役割**を担います。AI 開発者が評価ロジックを定義し、SRE/プラットフォームエンジニアがパイプラインのインフラストラクチャとスケジュールを管理します。

== 学習目標

このモジュールを修了すると、以下のことができるようになります：

* インナーループ (ノートブック) とアウターループ (パイプライン) の評価の違いを説明できる
* 評価パイプラインの定義を OpenShift AI にインポートできる
* 自動化された評価パイプラインを実行し、そのパラメーターを構成できる
* MLflow で自動評価結果を表示できる
* プロンプトのバージョン間で評価結果を比較することで、プロンプトのリグレッションを検出できる

== インナーループからアウターループへ

モジュール 5 では、Jupyter ノートブックのセルを実行して、プロスペクトエージェントを評価しました。このアプローチは開発中にはうまく機能しますが、いくつかの制限があります：

* **手動**: 誰かがノートブックを開いて「Run (実行)」をクリックする必要があります
* **再現性がない**: 結果はノートブック環境と実行した人に依存します
* **スケジュールできない**: モデルの更新やプロンプトの変更時に自動的にトリガーすることはできません

アウターループは、同じ評価ロジックを **AI パイプライン** (OpenShift AI プラットフォーム上で実行される一連のコンテナ化されたステップ) にパッケージ化することで、これらの問題を解決します。

[cols="1,1",options="header"]
|===
|インナーループ (モジュール 5) |アウターループ (モジュール 6)

|Jupyter ノートブック
|AI パイプライン (Kubeflow Pipelines)

|手動実行
|自動化、スケジュール設定、またはトリガー

|開発者のワークベンチ
|プラットフォームが管理するコンテナ

|インタラクティブな探索
|再現可能で監査可能な実行
|===

Red Hat OpenShift AI には、評価パイプラインを含むマルチステップの ML ワークフローをオーケストレーションするための https://docs.redhat.com/ja/documentation/red_hat_openshift_ai_self-managed/3.4/[Data Science Pipelines^] (Kubeflow Pipelines ベース) が含まれています。

== 演習 1: 評価パイプラインのインポート

mortgage-ai プロジェクトには、モジュール 5 のシンプルな評価を 4 つの自動化されたステップにパッケージ化した、コンパイル済みの評価パイプラインが含まれています。

. Red Hat OpenShift AI で、**Develop & Train** > **Pipelines** > **Pipeline definitions** に移動します：
+
image::eval16.png[OpenShift AI Pipeline definitions page showing no pipelines with Import pipeline button,link=self,window=blank,width=700]

. **Import pipeline** をクリックし、設定を行います：
+
--
* **Pipeline name (パイプライン名)**: `eval-simple-run`
* **Import by url** を選択します
* パイプラインの URL を貼り付けます：
+
[source,text]
----
https://raw.githubusercontent.com/rh-ai-quickstart/multi-agent-loan-origination/refs/heads/main/evaluations/pipelines_gen/simple-eval-pipeline.yaml
----
--
+
image::eval17.png[Import pipeline dialog with name eval-simple-run and Import by url selected,link=self,window=blank,width=500]
+
**Import pipeline** をクリックします。

. パイプライングラフには、4 つの自動化されたステップが表示されます：
+
image::eval18.png[Pipeline definition graph showing setup-mlflow-op then create-dataset-op then run-simple-eval-op then report-results-op,link=self,window=blank,width=700]
+
--
* **setup-mlflow-op**: MLflow トラッキング URI、ワークスペース、および実験を構成します
* **create-dataset-op**: MLflow サーバー上に評価データセットを作成します (モジュール 5 と同じ 6 つのテストケース)
* **run-simple-eval-op**: 3 つの決定論的スコアラー (`contains_expected`, `has_numeric_result`, `response_length`) を実行します
* **report-results-op**: 評価のサマリーを出力します
--

これは、モジュール 5 の演習 5 で手動で実行したのと同じ評価ですが、ノートブックなしで実行できるパイプラインとしてパッケージ化されています。

== 演習 4: 本番環境の前に悪いプロンプトをキャッチする

自動化されたパイプラインは、評価が継続的に実行されることを保証しますが、本当の効果が発揮されるのは、問題がユーザーに届く前にキャッチできたときです。

この演習では、現実的なシナリオをシミュレートします。チームメンバーがレイテンシを削減するためのプロンプトの変更を提案し、あなたは評価を使用して、その変更が応答の品質を密かに低下させることを発見します。

シナリオ: Fed Aura Capital の開発者は、プロスペクトエージェントが、一般的な知識で答えられる質問に対してもツールを呼び出していることに気づきました。彼らは「簡単な最適化」として、システムプロンプトの `TOOL USE (MANDATORY) (ツールの使用: 必須)` を `TOOL USE (OPTIONAL) (ツールの使用: オプション)` に変更し、エージェント自身の知識を優先し、本当に必要な場合のみツールを呼び出すように指示することを提案しました。

これは理にかなっているように聞こえます。レイテンシを減らすかもしれません。しかし、エージェントは引き続き正確で製品固有の応答を提供するでしょうか？確認してみましょう。

このノートブックは、プロンプトのリグレッション検出専用に構築されています。変更されたシステムプロンプトのバージョン 2 を登録し、モジュール 5 と同じ評価データセットを実行し、バージョン 1 のベースラインと結果を比較します。

=== 変更されたプロンプトを確認する

[start=3]
. **2. Create Modified Prompt (Version 2)** の下にあるセルを実行します。ノートブックはシステムプロンプトに微妙な変更を 1 つだけ加えます：
+
image::eval26.png[Modified system prompt Version 2 showing TOOL USE changed from MANDATORY to OPTIONAL,link=self,window=blank,width=700]
+
変更点: `TOOL USE (MANDATORY)` が `TOOL USE (OPTIONAL)` になります。エージェントは _"ツールを呼び出す代わりに、一般的な知識から回答することを優先してください"_ および _"自身の知識から本当に回答できない場合のみ、ツールを呼び出してください"_ と指示されるようになりました。
+
これは現実的なシナリオです。ツール呼び出しのレイテンシを減らすためにプロンプトを「最適化」する人は、ツールから取得したデータ (特定の製品の金利、融資限度額、支払い能力の計算) こそが応答を正確なものにしていることに気づいていないかもしれません。

=== MLflow にバージョン 2 を登録する

[start=4]
. **3. Register Version 2 in MLflow Prompt Registry** の下にあるセルを実行します。ノートブックは、説明的なコミットメッセージとともに、変更されたプロンプトをバージョン 2 として登録します：
+
image::eval27.png[Notebook registering Version 2 prompt in MLflow with commit message V2 Changed TOOL USE from MANDATORY to OPTIONAL,link=self,window=blank,width=500]
+
出力は、URI `prompts:/public-assistant-system-prompt/2` を持つ `public-assistant-system-prompt (version 2)` を確認します。タグに `"purpose": "regression-detection"` が含まれており、このバージョンがデプロイされるものではなくテスト中であることが明確になっていることに注意してください。

=== MLflow でプロンプトのバージョンを比較する

[start=5]
. **MLflow Console** タブに移動します。**mortgage-ai-eval** 実験に切り替えます：
+
image::nav-mortgageaieval-exp.png[]
+
. **Prompts** に移動し、**public-assistant-system-prompt** をクリックします。**Compare** タブをクリックします。

+
image::compare-prompts.png[]
+

. MLflow は、バージョン 2 (左) とバージョン 1 (右) の左右の diff (差分) を表示します：
+
image::eval28.png[MLflow Prompts Compare view showing side-by-side diff of Version 2 and Version 1 with red and green highlighting on the TOOL USE change,link=self,window=blank,width=700]
+
diff のハイライトにより、変更箇所がすぐにわかります。`TOOL USE` セクションが `(MANDATORY)` から `(OPTIONAL)` に変更され、指示が _"you MUST call the product_info tool (product_info ツールを呼び出す必要があります)"_ から _"you may call the product_info tool, but prefer answering from your general knowledge (product_info ツールを呼び出してもかまいませんが、一般的な知識から回答することを優先してください)"_ に変更されています。
+
これは、プルリクエストでコードの diff をレビューするのと同じ体験ですが、プロンプトに対して行われます。これまで、Fed Aura Capital でのプロンプトの変更は、YAML ファイル内の追跡されていないテキスト編集でした。今ではすべての変更がバージョン管理され、diff が可能になり、評価結果にリンクされています。

=== バージョン 2 に対して評価を実行する

[start=6]
. ノートブックに戻ります。**#5** から **7. Run Evaluation with V2 Prompt** までのセルを実行します。このセルは、モジュール 5 と同じ 6 つのテストケースと 3 つの決定論的スコアラーを実行しますが、変更された v2 プロンプトを使用します：
+
image::eval29.png[Notebook running V2 evaluation showing 6 examples and 3 scorers with results contains_expected 83 percent has_numeric_result 50 percent response_length 100 percent,link=self,window=blank,width=500]
+
結果は、モジュール 5 のベースラインと比較してリグレッションを示す可能性が高いです。`contains_expected` の低下 (エージェントが期待される製品キーワードを一貫して言及しなくなる可能性がある) と `has_numeric_result` の変化 (エージェントがツールから取得した具体的な情報ではなく、一般的な回答をしていることを示唆) を探してください。正確な割合は異なる場合がありますが、劣化のパターンは目に見えるはずです。

=== 結論

無害な最適化のように見えたプロンプトの変更は、応答の正確さに**測定可能なリグレッション**を引き起こしたでしょう。モジュール 5 と 6 で構築した評価フレームワークがなければ、この変更は手動での簡単なテスト (「まだ質問に答えているし、問題なさそう」) に基づいて本番環境にデプロイされていたでしょう。Fed Aura Capital のプロスペクトエージェントは、特定の製品情報の代わりに一般的な住宅ローンのアドバイスを提供し始め、顧客を誤解させ、コンプライアンスリスクを生み出していた可能性があります。

評価インフラストラクチャは、リグレッションが 1 人のユーザーに届く前にそれをキャッチしました。これが AgentOps の中心的な価値です。**可用性だけでなく、品質への可視性**です。

== モジュールのまとめ

**達成したこと:**

* コンパイル済みの評価パイプラインを OpenShift AI にインポートしました
* 自動化された評価パイプラインを設定して実行しました
* ノートブック駆動の結果と並べて、MLflow で自動評価結果を表示しました
* バージョン 1 とバージョン 2 の評価結果を比較することで、本番環境の前にプロンプトのリグレッションを検出しました

**重要なポイント:**

* インナーループ (ノートブック) は探索と開発のためのものであり、アウターループ (パイプライン) は自動化と本番環境のためのものです
* OpenShift AI Pipelines は、同じ評価ロジックを、再現可能でスケジュール可能なコンテナ化された実行としてパッケージ化します
* MLflow のプロンプトレジストリを評価と組み合わせることで、品質ゲート (品質の関所) が作成されます。すべてのプロンプトの変更は、デプロイ前にテストされ、差分が取得され、比較可能になります。
* 評価は、手動テストでは見逃される微妙なリグレッションをキャッチし、悪いプロンプトが本番環境に到達するのを防ぎます

**次のステップ:**

まとめ (Conclusion) では、モジュール 1 のブラックボックスからメトリクス、トレース、評価、および自動化されたパイプラインに至るまでの、完全なオブザーバビリティの旅を振り返り、AgentOps の実践を継続するためのリソースを提供します。
