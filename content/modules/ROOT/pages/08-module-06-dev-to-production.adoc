====
**本模块是可选的**，建立在模块 5 的基础上。它展示了如何将评估自动化集成到 CI/CD 流水线中，以实现持续的质量监控。
====

在模块 5 中，你从 Jupyter notebook 手动运行评估，这是 AI 开发者工作流程中的*内循环*。但手动评估无法扩展。在生产环境中，你需要能够自动运行、按计划或作为 CI/CD 流水线一部分运行的评估。

在本模块中，你将通过在 Red Hat OpenShift AI 中导入和运行评估流水线，从内循环转移到*外循环*。你在模块 5 中使用的相同的评分器、数据集和 MLflow 集成现在作为自动化流水线运行。无需 notebook。

TIP：在本模块中，你需要扮演**两个角色**：AI 开发者定义评估逻辑，而 SRE/平台工程师管理流水线基础设施和调度。

== 学习目标

完成本模块后，你将能够：

* 解释内循环（notebook）和外循环（流水线）评估之间的区别
* 将评估流水线定义导入 OpenShift AI
* 运行自动化评估流水线并配置其参数
* 在 MLflow 中查看自动化评估结果
* 通过比较不同 prompt 版本的评估结果来检测 prompt 回归

== 从内循环到外循环

在模块 5 中，你通过在 Jupyter notebook 中运行单元格来评估潜在客户代理。这种方法在开发期间效果很好，但也有局限性：

* **手动操作**：有人需要打开 notebook 并点击运行
* **不可复现**：结果取决于 notebook 环境和运行者
* **不可调度**：你无法在模型更新或 prompt 更改时自动触发它

外循环通过将相同的评估逻辑打包到**AI 流水线**中来解决这些问题，这是一系列在 OpenShift AI 平台上运行的容器化步骤。

[cols="1,1",options="header"]
|===
|内循环（模块 5） |外循环（模块 6）

|Jupyter notebook
|AI 流水线（Kubeflow Pipelines）

|手动执行
|自动化、计划或触发执行

|开发者工作台
|平台管理的容器

|交互式探索
|可复现、可审计的运行
|===

Red Hat OpenShift AI 包含 https://docs.redhat.com/en/documentation/red_hat_openshift_ai_self-managed/3.4/[数据科学流水线^]（基于 Kubeflow Pipelines），用于编排多步骤 ML 工作流，包括评估流水线。

== 练习 4：在生产前捕获不良 prompt

自动化流水线确保评估持续运行，但真正的价值在于它们在问题影响用户之前就发现它。

在本练习中，你将模拟一个真实的场景：团队成员提出一个 prompt 更改以减少延迟，而你使用评估发现该更改会悄然降低响应质量。

场景：Fed Aura Capital 的一名开发者注意到潜在客户代理调用工具来回答它可以从常识中回答的问题。他们提出一个"快速优化"——将系统 prompt 中的 `TOOL USE (MANDATORY)` 改为 `TOOL USE (OPTIONAL)`，告诉代理更倾向于自己的知识，只有在真正必要时才调用工具。

这听起来很合理。它可能会减少延迟。但代理还能提供准确的、特定产品的响应吗？让我们找出答案。

=== 查看修改后的 prompt

[start=3]
. 运行 **2. 创建修改后的 Prompt（版本 2）** 下的单元格。notebook 对系统 prompt 进行了一个微妙的更改：
+

更改：`TOOL USE (MANDATORY)` 变为 `TOOL USE (OPTIONAL)`。代理现在被告知 _"更倾向于从你的常识回答，而不是调用工具"_ 和 _"只有在你确实无法从自己的知识回答时才调用工具。"_ +
这是一个真实的场景。有人可能会"优化" prompt 以减少工具调用延迟，而没有意识到工具源数据（特定产品费率、贷款限额、负担能力计算）才是使响应准确的原因。

=== 结论

看起来像无害优化的 prompt 更改会导致响应准确性的**可衡量回归**。如果没有你在模块 5 和 6 中构建的评估框架，此更改将基于快速手动测试（"它仍然回答问题，看起来不错"）部署到生产。Fed Aura Capital 的潜在客户代理将开始提供通用的抵押贷款建议，而不是特定产品信息，可能会误导客户并产生合规风险。

评估基础设施在问题影响任何用户之前就捕获了回归。这是 AgentOps 的核心价值：**对质量的可见性，而不仅仅是可用性**。

* 评估捕获手动测试会错过的微妙回归，防止不良 prompt 到达生产环境
