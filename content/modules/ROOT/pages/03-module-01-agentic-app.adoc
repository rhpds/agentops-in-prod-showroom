= Module 1: The agentic app and why observability matters
:navtitle: Module 1: The Agentic App
:source-highlighter: rouge
:toc: macro
:toclevels: 1

Agentic AI apps don't fail silently -- they fail distributedly. In this module, you'll deploy and explore the mortgage-ai multi-agent application and understand why traditional monitoring approaches fall short for these complex systems.

Fed-Aura needs end-to-end visibility into their multi-agent workflows, and you've been tasked with evaluating how observability can help. Before implementing solutions, you need to understand what you're working with.

In this module, you'll experience firsthand why multi-agent systems require a different approach to observability.

* Recognize the key failure modes in multi-agent architectures

== Exercise 1: Deploy the mortgage-ai application

The mortgage-ai multi-agent system is packaged as a Helm chart. Let's deploy it to your namespace.

. First, log in to OpenShift:
+
[source,bash]
----
oc login {openshift_api_url} -u {user} -p {password}
----

. Create and switch to your workspace namespace:
+
[source,bash]
----
oc new-project wksp-{user} || oc project wksp-{user}
----

. Clone the multi-agent loan origination repository:
+
[source,bash]
----
git clone https://github.com/rh-ai-quickstart/multi-agent-loan-origination.git
cd multi-agent-loan-origination
----

. Create your environment configuration from the example:
+
[source,bash]
----
cp .env.example .env
----

. Edit `.env` to configure your LLM endpoint:
+
[source,env]
----
LLM_BASE_URL=http://localhost:1234/v1
LLM_API_KEY=not-needed
LLM_MODEL_FAST=qwen3-30b-a3b
LLM_MODEL_CAPABLE=qwen3-30b-a3b
----

. Source the environment and deploy using Helm:
+
[source,bash]
----
set -a && source .env && set +a

helm install mortgage-ai ./deploy/helm/mortgage-ai \
  -n wksp-{user} --create-namespace \
  --set secrets.AUTH_DISABLED="${AUTH_DISABLED:-true}" \
  --set secrets.LLM_BASE_URL="${LLM_BASE_URL}" \
  --set secrets.LLM_API_KEY="${LLM_API_KEY}" \
  --set secrets.LLM_MODEL_FAST="${LLM_MODEL_FAST}" \
  --set secrets.LLM_MODEL_CAPABLE="${LLM_MODEL_CAPABLE}"
----

. Wait for all deployments to become ready:
+
[source,bash]
----
oc rollout status deployment/mortgage-ai-api -n wksp-{user}
oc rollout status deployment/mortgage-ai-ui -n wksp-{user}
----

=== Verify

== Exercise 2: Explore the multi-agent architecture

The mortgage-ai system serves five distinct agent personas through a single API deployment. Each persona handles different aspects of the mortgage lending workflow.

|mortgage-ai-db

=== Key AI patterns

This application demonstrates production-ready AI patterns for regulated industries:

* **Multi-agent orchestration** - Five LangGraph agents with role-scoped tools and RBAC enforcement
* **Compliance knowledge base** - pgvector RAG with tiered boosting (federal regulations > agency guidelines > internal policies)
* **Model routing** - Complexity-based routing between fast and capable LLM tiers
* **Comprehensive audit trail** - Hash-chained, append-only audit events with MLflow trace correlation
* **PII masking** - Middleware-based masking for executive roles (SSN, DOB, account numbers)
* **Safety shields** - Input and output content filters with escalation pattern detection

== Exercise 4: Experience distributed failures

Now let's understand why observability is critical by observing what happens when things go wrong in a multi-agent system.

. Submit a test loan inquiry through the API:
+
[source,bash]
----
curl -X POST https://${MORTGAGE_API}/api/prospect/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "I want to apply for a mortgage"}'
----

. Check the application status -- notice the lack of visibility:
+
[source,bash]
----
# Where did the request go?
# Which agents processed it?
# How long did each step take?
# We don't know!
----

. Try to find what happened using traditional logs:
+
[source,bash]
----
# Check API logs
oc logs -l app.kubernetes.io/name=mortgage-ai-api --tail=50 -n wksp-{user}

# Check database logs
oc logs -l app.kubernetes.io/name=mortgage-ai-db --tail=50 -n wksp-{user}
----
+
IMPORTANT: Notice how difficult it is to correlate events across services using logs alone. Each component has its own log stream with no common correlation ID.

=== The observability challenge

Without proper instrumentation, you face these challenges:

* **No request correlation**: Logs from different services cannot be connected
* **Hidden latency**: You can't identify which component is causing delays
* **Silent failures**: Tool calls may fail without surfacing in logs
* **No decision visibility**: You can't see why an agent made a particular decision

== Troubleshooting

**Issue**: Helm install fails with namespace error

→ **Solution**:

. Ensure the namespace exists: `oc new-project wksp-{user}`
. Verify you have permissions: `oc auth can-i create deployments`

**Issue**: mortgage-ai-api pod not starting

→ **Solution**:

. Check pod events: `oc describe pod -l app.kubernetes.io/name=mortgage-ai-api`
. View init container logs: `oc logs <pod-name> -c wait-for-database`
. Verify database is running: `oc get pods -l app.kubernetes.io/name=mortgage-ai-db`

**Issue**: Cannot access UI route

→ **Solution**:

. Verify route exists: `oc get routes`
. Check route TLS: `oc describe route mortgage-ai-ui-route`
. Test service directly: `oc port-forward svc/mortgage-ai-ui 8080:8080`

**Issue**: Cannot connect to OpenShift cluster

→ **Solution**:

. Verify your credentials are correct
. Check network connectivity: `ping api.cluster.example.com`
. If using VPN, ensure it's connected
. Try accessing via bastion: `ssh {bastion_user}@{bastion_host}`
