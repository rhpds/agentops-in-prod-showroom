= Module 1: The agentic app and why observability matters
:navtitle: Module 1: The Agentic App
:source-highlighter: rouge
:toc: macro
:toclevels: 1

Agentic AI apps don't fail silently -- they fail distributedly. In this module, you'll explore the Acme FinTech multi-agent mortgage lending application and understand why traditional monitoring approaches fall short for these complex systems.

Acme FinTech needs end-to-end visibility into their multi-agent workflows, and you've been tasked with evaluating how observability can help. Before implementing solutions, you need to understand what you're working with.

In this module, you'll experience firsthand why multi-agent systems require a different approach to observability.

== Learning objectives

By the end of this module, you'll be able to:

* Describe the architecture of the Acme FinTech multi-agent mortgage lending system
* Identify the five distinct agent personas and their responsibilities
* Explain why distributed AI systems require specialized observability approaches
* Recognize the key failure modes in multi-agent architectures

== Exercise 2: Understand the agent personas

Each agent in the Acme FinTech system serves a specific role in the mortgage lending lifecycle. Understanding these roles is crucial for effective observability.

=== The five agent personas

[cols="1,2,2",options="header"]
|===
|Agent |Persona |Responsibility

|Prospect Agent
|Potential customer
|Handle initial inquiries, provide rate estimates, qualify leads

|Borrower Agent
|Loan applicant
|Manage application intake, collect documentation, validate submissions

|Loan Officer Agent
|Internal staff
|Pipeline management, application review, customer communication

|Underwriter Agent
|Risk assessor
|Compliance checks, risk assessment, approval decisions

|Executive Agent
|Management
|Analytics, reporting, portfolio oversight
|===

. Query the prospect agent to see its capabilities:
+
[source,bash]
----
PROSPECT_URL=$(oc get route prospect-agent -o jsonpath='{.spec.host}')
curl -s https://${PROSPECT_URL}/api/capabilities | jq .
----

. Review the agent's MCP tool integrations:
+
[source,bash]
----
curl -s https://${PROSPECT_URL}/api/tools | jq '.tools[] | {name, description}'
----

=== MCP tool integrations

The agents communicate with external services through Model Context Protocol (MCP) servers:

* **MCP Compliance Server**: Handles HMDA, ECOA, TRID, ATR/QM, and FCRA compliance checks
* **MCP Credit Server**: Retrieves credit scores and financial data

. Check the MCP server status:
+
[source,bash]
----
oc get pods -l app=mcp-server
----

=== Verify

----
curl -s https://${PROSPECT_URL}/health
----

Expected output:
----
{"status": "healthy", "agent": "prospect", "version": "1.0.0"}
----

✓ Agent version is displayed

== Exercise 3: Experience distributed failures

Now let's understand why observability is critical by observing what happens when things go wrong in a multi-agent system.

. Submit a test loan inquiry through the prospect agent:
+
[source,bash]
----
curl -X POST https://${PROSPECT_URL}/api/inquiry \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Jane Doe",
    "email": "jane.doe@example.com",
    "loan_amount": 350000,
    "property_type": "single_family"
  }'
----

. Check the application status -- notice the lack of visibility:
+
[source,bash]
----
# Where did the request go?
# Which agents processed it?
# How long did each step take?
# We don't know!
----

. Try to find what happened using traditional logs:
+
[source,bash]
----
# Check prospect agent logs
oc logs -l app=prospect-agent --tail=50

# Check borrower agent logs
oc logs -l app=borrower-agent --tail=50

# Check underwriter agent logs
oc logs -l app=underwriter-agent --tail=50
----
+
IMPORTANT: Notice how difficult it is to correlate events across multiple agents using logs alone. Each agent has its own log stream with no common correlation ID.

=== The observability challenge

Without proper instrumentation, you face these challenges:

* **No request correlation**: Logs from different agents cannot be connected
* **Hidden latency**: You can't identify which agent or tool is causing delays
* **Silent failures**: MCP tool failures may not surface in agent logs
* **No decision visibility**: You can't see why an agent made a particular decision

== Troubleshooting

**Issue**: Cannot connect to OpenShift cluster
**Solution**:

. Verify your credentials are correct
. Check network connectivity: `ping api.cluster.example.com`
. If using VPN, ensure it's connected
. Try accessing via bastion: `ssh {bastion_user}@{bastion_host}`

**Issue**: Agent pods not running
**Solution**:

. Check pod status: `oc get pods`
. View pod events: `oc describe pod <pod-name>`
. Check for resource constraints: `oc get events --sort-by='.lastTimestamp'`

**Issue**: Cannot access agent routes
**Solution**:

. Verify route exists: `oc get routes`
. Check route TLS configuration: `oc describe route <route-name>`
. Test from within cluster: `oc debug deployment/prospect-agent -- curl localhost:8080/health`
