= 模块 1：智能体应用与可观测性的必要性
:imagesdir: ../assets/images
:navtitle: Module 1: The Agentic App
:toc: macro
:toclevels: 1

AI 智能体应用不会简单直接报错，故障往往分散在整个分布式链路中。本模块将带你体验已部署完成的抵押贷款多智能体应用，并理解传统监控手段为何无法适配这类复杂 AI 系统。

首先明确：什么是 AI 智能体？AI 智能体依托大语言模型（LLM）完成任务推理、自主选择调用工具并执行自主操作，区别于传统接口、基础聊天机器人这类简单一问一答模式。当多个智能体协同工作，各自配备专属工具、承担独立业务职责时，就构成多智能体系统。这类系统业务能力强大，但内部链路复杂，排障与可视化难度大幅提升。

联邦奥若资本需要多智能体全流程可视化能力，本次由你负责验证可观测体系的落地价值。在搭建解决方案前，你需要先熟悉整套应用架构。

== 学习目标

完成本模块学习后，你将具备以下能力：

* 描述抵押贷款多智能体系统整体架构

* 说明分布式 AI 系统需要专用可观测方案的原因
* 识别多智能体架构中常见的故障模式（系统异常、性能衰减场景）

=== 请求完整流转链路

**请求路径:** User → UI → WebSocket → API router → Specific agent → LangGraph workflow → Tools (DB, MCP, LLM) → Response

**示例场景 (高管提问： "What's the portfolio health?"):**

. 用户在前端页面输入问题
. WebSocket 根据登录高管身份，路由请求至/api/ceo/chat接口
. 高管智能体（LangGraph 流程）接收提问
. 智能体自主判定需要调用工具/tools：`get_pipeline_summary`, `calculate_pull_through_rate`(获取业务汇总数据,计算贷款转化率)
. 工具分别查询数据库或调用外部 MCP tools
. 智能体多次调用大模型，结合工具返回数据完成推理分析
. 整合结论后将回答返回前端用户

**可观测性核心痛点:** 用户单次提问，背后可能触发 5 次以上大模型调用、十余次工具调用、多轮数据库查询。一旦结果异常或流程报错，必须完整追溯整条决策链路，才能定位根因。

重点: **多智能体架构常见故障模式** +
理解系统故障形式，是搭建有效可观测体系的前提: +
 +
• **工具调用静默性失败**: MCP 工具返回空数据，但智能体继续基于残缺信息生成回复，无任何报错提示 +
• **延迟连锁叠加**: 数据库查询缓慢拖慢大模型调用，最终整体响应超时，无法定位耗时瓶颈步骤 +
• **上下文溢出**: 智能体向大模型传入数据量超限，调用失败仅返回模糊报错，用户仅看到通用超时提示 +
• **非确定性故障**: 相同提问因大模型输出随机性得到不同结果，问题难以复现 +
• **分布式连锁故障**: 某一个智能体工具调用失败，影响下游智能体流程，且错误无法清晰传递

=== 校验服务部署状态

正式实操应用前，先确认所有组件正常运行，校验两项内容：OpenShift 容器就绪状态、API 服务数据库连通性

. 切换至 **Terminal** tab. 查看 Pod 运行状态:
+
[source,bash,role=execute,subs=attributes+]
----
oc get pods -n {user_project}
----
+
该命令展示当前命名空间下所有容器就绪状态。正常状态为Running，就绪数1/1或2/2；若显示CrashLoopBackOff、Error、0/1，代表部署未完成。.

. 校验 API 服务健康检查接口:
+
[source,console,role=execute,subs=attributes+]
----
MORTGAGE_HEALTH=$(oc get route mortgage-ai-api-health-route -n {user_project} -o jsonpath='{.spec.host}')
curl -sk https://$\{MORTGAGE_HEALTH}/health/ | jq -r .
----
+
健康检查会验证两大核心依赖：FastAPI 服务自身、PostgreSQL 数据库连接(数据库存储业务状态、RAG 嵌入、审计记录)。
+
正常返回示例:

=== 生成多轮对话，用于后续链路追踪分析

[start=5]

----

. 接着再次提问:
+
[source,console,role=execute,subs=attributes+]

----

每一条提问都会触发不同后台工具调用。完成后本次高管会话包含三轮对话，覆盖业务总量、拒贷分析、专员绩效三类数据，模块 4 中将完整追溯整条对话全链路。

=== 可观测性核心难题

页面返回结果看似完整，但后台存在大量无法直观获取的信息:

* 由哪一个**智能体**处理本次提问？是单个智能体？还是多智能体协同处理？
* 智能体调用了哪些工具**tools**来获取业务总量、拒贷率、绩效指标？
* 每一步操作耗时**多久**？是大模型调用缓慢，还是工具tool调用造成延迟？
* 若回复数据**出错**，该如何追溯定位根因？
* 若工具调用**失败性静默**，你能否察觉？

缺少专业埋点与可观测体系，以上问题全部无法解答。前端仅展示加工后的最终回答，完整决策链路（智能体路由、工具调用、大模型请求、数据查询）完全是黑盒。

**传统监控方案的局限性:**

传统应用监控仅采集 HTTP 请求、错误率、响应耗时。针对mortgage-ai API，传统监控只能看到:

* `POST /api/ceo/chat` → 200 OK, 2.3s response time

但无法获取以下关键信息:

* 高管智能体具体调用了哪些工具 (`get_pipeline_summary`, `calculate_pull_through_rate`)
* 总共发起多少次大模型调用（3 次还是 8 次）
* 2.3 秒总耗时中，1.8 秒消耗在哪一步操作
* 智能体是否从数据库读取到准确业务数据
* 是否存在工具调用静默性失败，但智能体依旧生成回答

这正是 AgentOps 需要专用可观测能力的核心原因：我们需要看透智能体内部完整决策流程，而非仅监控外层 HTTP 接口。后续模块将基于可观测三大支柱，讲解如何埋点实现全链路可视化。

[%collapsible]
.底层原理：可用于生产的AI模式
====
本应用展示了受强监管行业落地 AI 系统的核心实践模式:

* **多智能体编排**: 基于 LangGraph 构建 5 个业务智能体，工具按角色隔离，配套 RBAC 增强管控
* **合规知识库**: 依托 pgvector 实现检索增强生成（RAG），采用分层提升策略：联邦法规 > 监管机构指引 > 企业内部制度
* **模型路由**: 根据业务复杂度自动分流，在轻量快速大模型与高性能大模型层之间动态切换
* **完整审计链路**: 采用哈希链、仅追加写入的审计事件，并与 MLflow 链路追踪数据关联打通
* **敏感个人信息脱敏**: 基于中间件统一脱敏高管视图中的隐私数据（社保号、出生日期、账户编号）
* **安全防护屏障**: 输入 / 输出内容过滤，可识别风险升级类异常对话模式
====
