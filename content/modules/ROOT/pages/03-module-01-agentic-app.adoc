= モジュール 1: エージェント型アプリとオブザーバビリティが重要な理由
:imagesdir: ../assets/images
:navtitle: モジュール 1: エージェント型アプリ
:toc: macro
:toclevels: 1

エージェント型AIアプリは静かに失敗するのではなく、分散して失敗します。このモジュールでは、事前にデプロイされた mortgage-ai マルチエージェントアプリケーションを探索し、これらの複雑なシステムに対して従来の監視アプローチがなぜ不十分なのかを理解します。

しかしその前に、AIエージェントとは正確には何でしょうか？ **AIエージェント**とは、タスクについて推論し、どのツールを呼び出すかを決定し、自律的なアクションを実行するために大規模言語モデル（LLM）を使用するシステムであり、従来のAPIや基本的なチャットボットのような単純なリクエスト/レスポンスパターンを超えたものです。複数のエージェントが連携し、それぞれが独自のツールと責任を持つ場合、機能は高いものの、観察やデバッグがはるかに困難な**マルチエージェントシステム**になります。

Fed Aura Capitalは、自社のマルチエージェントワークフローに対するエンドツーエンドの可視性を必要としており、あなたはオブザーバビリティがどのように役立つかを評価する任務を負っています。ソリューションを実装する前に、自分が何を扱っているのかを理解する必要があります。

== 学習目標

このモジュールを修了すると、以下のことができるようになります：

* マルチエージェントの住宅ローン融資システムのアーキテクチャを説明できる
* 5つの異なるエージェントのペルソナとその責任を特定できる
* 分散型AIシステムがなぜ特化したオブザーバビリティアプローチを必要とするのかを説明できる
* マルチエージェントアーキテクチャにおける主要な障害モード（システムが失敗または劣化するパターン）を認識できる

== 演習 2: マルチエージェントアーキテクチャの探索

=== アーキテクチャの理解

=== リクエストのフロー

**リクエストパス:** ユーザー → UI → WebSocket → APIルーター → 特定のエージェント → LangGraph ワークフロー → ツール (DB, MCP, LLM) → 応答

**例 (CEOが「ポートフォリオの健全性は？」と尋ねる場合):**

. ユーザーがUIで質問をする
. WebSocketが認証されたロールに基づいて `/api/ceo/chat` にルーティングする
. CEOエージェント（LangGraphワークフロー）が質問を受け取る
. エージェントが呼び出すツールを決定する: `get_pipeline_summary`、`calculate_pull_through_rate`
. 各ツールがデータベースにクエリを実行するか、外部のMCPツールを呼び出す場合がある
. エージェントはツールの結果について推論するためにLLMを複数回呼び出す
. 最終的な応答がユーザーに返される

**これがオブザーバビリティにとって重要な理由:** 1つのユーザーの質問が、5回以上のLLM呼び出し、10回以上のツール呼び出し、そして複数のデータベースクエリをトリガーする可能性があります。何かが失敗したり、間違ったデータを返したりした場合、根本原因を見つけるために意思決定パス全体をトレースする必要があります。

IMPORTANT: **マルチエージェントアーキテクチャにおける一般的な障害モード** +
効果的なオブザーバビリティを実装するには、これらのシステムがどのように失敗するかを理解することが重要です： +
 +
• **サイレントなツールの障害**: MCPツールが空のデータを返しても、エージェントはそのまま処理を続行し、不完全な情報に基づいて応答を生成してしまう +
• **カスケードするレイテンシ**: データベースクエリが遅いとLLMの呼び出しが遅れ、応答が遅延するが、どのステップがボトルネックを引き起こしたかを特定できない +
• **コンテキストのオーバーフロー**: エージェントがLLMに渡そうとするデータ量が多すぎると、不可解なエラーで呼び出しが失敗し、ユーザーには一般的なタイムアウトが表示される +
• **非決定的な障害**: LLMのばらつきにより、同じ質問でも異なる結果が生じるため、バグの再現が困難になる +
• **分散された障害**: あるエージェントのツール呼び出しが失敗すると、明確なエラーの伝播なしに下流のエージェントに影響を及ぼす

=== デプロイメントの検証

アプリケーションを探索する前に、すべてのコンポーネントが実行されており正常であることを確認しましょう。ここでは2つのことを確認します。OpenShiftのポッドが準備完了（Ready）であることと、APIがデータベースに正常に接続できることです。

. **Terminal** タブに移動します。ポッドとそのステータスを表示します：
+
[source,bash,role=execute,subs=attributes+]
----
oc get pods -n {user_project}
----
+
このコマンドは、ネームスペース内のすべてのポッドとその準備状況（readiness status）を表示します。すべてのポッドが `Running` を示し、コンテナが `1/1` または `2/2` で準備完了になっているはずです。いずれかのポッドが `CrashLoopBackOff`、`Error`、または `0/1` を示している場合、デプロイメントは正常に完了していません。

. APIサービスのヘルスエンドポイントを確認します：
+
[source,console,role=execute,subs=attributes+]
----
MORTGAGE_HEALTH=$(oc get route mortgage-ai-api-health-route -n {user_project} -o jsonpath='{.spec.host}')
curl -sk https://$\{MORTGAGE_HEALTH}/health/ | jq -r .
----
+
このヘルスチェックは、マルチエージェントシステムにとって重要な2つの依存関係を検証します。FastAPIサービス自体と、PostgreSQLデータベース（アプリケーションの状態、RAG用の埋め込み、および監査証跡を保存する）への接続です。
+
予想される出力：
+
[source,json]
----
[
  {
    "name": "API",
    "status": "healthy",
    "message": "API is running",
    "version": "0.1.0",
    "start_time": "2026-04-07T22:21:27.657181+00:00"
  },
  {
    "name": "Database",
    "status": "healthy",
    "message": "PostgreSQL connection successful",
    "version": "0.1.0",
    "start_time": "2026-04-07T22:21:19.877102+00:00"
  }
]
----
+
**この結果が意味するもの:** APIとDatabaseコンポーネントの両方が `"status": "healthy"` を報告しています。これは、FastAPIポッドが実行されており、PostgreSQLへの接続を確立できることを確認するものです。正常なデータベース接続がないと、エージェントはナレッジベースにアクセスしたり、アプリケーションデータを取得したり、RAGワークフローを実行したりできません。どちらかのコンポーネントが `"healthy"` 以外のステータスを示している場合は、先に進む前にそのサービスをトラブルシューティングしてください。

=== オブザーバビリティの課題

応答は素晴らしいように見えます。しかし、裏で何が起こったのかを少し考えてみてください。

* どの**エージェント**があなたの質問を処理しましたか？単一のエージェントでしたか、それとも複数のエージェントが連携しましたか？
* パイプラインのデータ、拒否率、パフォーマンスメトリクスを収集するために、エージェントはどの**ツール**を呼び出しましたか？
* 各ステップに**どれくらいの時間**がかかりましたか？LLMの呼び出しは速かったですか、それともツール呼び出しによってレイテンシが追加されましたか？
* もし応答が**間違っていた**ら？根本原因までどのようにトレースバックしますか？
* ツール呼び出しが**サイレントに失敗**したらどうなりますか？あなたはそれに気づくことができますか？

適切なオブザーバビリティのための計装(instrumentation)がなければ、これらの質問に答えることはできません。アプリケーションは洗練された応答を提供しますが、意思決定プロセス全体（エージェントのルーティング、ツールの呼び出し、LLMの呼び出し、データの取得）はブラックボックスのままです。

**従来の監視では不十分な理由：**

従来のアプリケーション監視では、HTTPリクエスト、エラー率、応答時間を追跡します。mortgage-ai APIの場合、以下のような情報が表示されます：

* `POST /api/ceo/chat` → 200 OK, 応答時間 2.3秒

しかし、以下の情報は表示されません：

* CEOエージェントがどのツールを呼び出したか（`get_pipeline_summary`, `calculate_pull_through_rate`）
* LLM呼び出しが何回発生したか（3回ですか、それとも8回ですか？）
* 全体で2.3秒のうち、1.8秒かかったのはどの呼び出しだったか
* エージェントがデータベースから正しいデータを取得したかどうか
* ツール呼び出しがサイレントに失敗したにもかかわらず、エージェントが応答を生成したかどうか

これが、AgentOpsに特化したオブザーバビリティが必要な理由です。単なるHTTPのラッパーではなく、意思決定プロセスの内部を見る必要があるのです。次のモジュールでは、オブザーバビリティの3本柱を使用してこの可視性を計装する方法を学びます。

[%collapsible]
.内部の仕組み: 本番環境対応のAIパターン
====
このアプリケーションは、規制産業向けの重要なパターンを示しています：

* **マルチエージェントオーケストレーション**: ロールスコープのツールとRBACの強制を備えた5つのLangGraphエージェント
* **コンプライアンスナレッジベース**: 階層化されたブースティング（連邦規制 > 政府機関のガイドライン > 社内ポリシー）を備えたpgvectorを使用するRAG
* **モデルルーティング**: 高速なLLM層と高性能なLLM層の間の複雑さに基づくルーティング
* **包括的な監査証跡**: MLflowのトレースの相関付けを備えた、ハッシュチェーンによる追記型監査イベント
* **PIIマスク処理**: エグゼクティブロール向けのミドルウェアベースのマスキング（SSN(社会保障番号)、DOB(生年月日)、口座番号）
* **セーフティシールド**: エスカレーションパターンの検出を備えた入力および出力コンテンツフィルター
====

== モジュールのまとめ

**達成したこと:**

* 5つのエージェントのペルソナとマルチエージェントアーキテクチャの探索
* アプリケーションUIを介したエージェントとの対話
* 分散型AIシステムにおけるオブザーバビリティのギャップの体験

**重要なポイント:**

* マルチエージェントシステムは、複数のコンポーネントにわたって意思決定を分散させます
* 単一のAPIで、異なる機能を持つ複数のエージェントペルソナを提供できます
* AgentOpsには特化したオブザーバビリティのアプローチが必要です

**次のステップ:**

モジュール2では、オブザーバビリティの3本柱（メトリクス、ログ、トレース）と、SRE/プラットフォームエンジニアリングとAI開発者/エンジニアという異なるペルソナがこれらのシステムの監視にどのようにアプローチするかについて紹介します。
